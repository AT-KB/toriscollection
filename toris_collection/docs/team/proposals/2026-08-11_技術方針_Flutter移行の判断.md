# 技術方針 — Flutter 移行の判断（2026-08-11）

作成: PJ管理部 / 位置づけ: 提案書。**着手前の承認が必要**。
CEO の判断基準: **ピボットのしやすさ / 維持コストの低さ**。その2点で C（Flutter）を選択。

**一行**: 行き先は C で合意。ただし**いきなり全面移行はしない**。
**いちばん危ないところ（音）を先に1つだけ試す**。そこが通れば残りは素直に進む。

---

## 1. なぜ C が正しいか（CEO の基準に照らして）

### 維持コスト — いまの構成は「低い」どころか3層ある
現在、実質3つのスタックとサーバー1台を同時に維持している。

```
Python / Streamlit  ← アプリ本体
Capacitor の殻      ← WebView を包むだけの層
ネイティブ Java     ← WebView では作れないもの(目覚まし・スプラッシュ・watchdog)
Render (サーバー)   ← これが無いとアプリが起動しない
```

**引き継ぎ書に残っている事故の大半がサーバー由来である。**
- WebSocket 不通で真っ白（2026-07-13・重大インシデント扱い）
- コールドスタート **22.7秒**（無料プラン）
- それを埋めるための keep-warm cron（GitHub Actions が間引くので5分ループに変更）
- CORS 設定、User-Agent の埋め込みマーカー、WebView の描画停止…

**Flutter に移ると、この4層のうち3つが消える。** サーバーも要らなくなる
（データは端末内で完結し、必要になったら後から足せる）。

### ピボットのしやすさ — いまの構成が制約そのものになっている
この2日で分かったとおり、**やりたいことが出るたびに壁に当たっている**。
- 目覚まし → WebView では作れず、ネイティブに書いた
- 環境音の質 → WebAudio の合成では足りず、素材が要る
- 起動の速さ・オフライン → 構造的に不可能

今後「通知」「ウィジェット」「iOS」に触れるたび、同じ壁が来る。
**Streamlit はフォームとデータ表示には最速だが、音とネイティブ連携には最も弱い。**
そしてこの商品は、まさに音とネイティブ連携の商品になりつつある。

### おまけ: 収益化もきれいになる
Flutter は `google_mobile_ads` が公式提供。いまの Capacitor プラグイン経由より素直。

## 2. ⚠️ 唯一にして最大のリスク — 音

**移行で本当に難しいのは UI ではなく、ラジオの音響エンジンである。**

いま `radio.py` の中で WebAudio を使って作っているもの:
- 鳥ごとの**ゲート**（無音時のノイズを切る）と **AGC**（録音ごとの音量差を吸収）
- **リバーブ**（畳み込み）と深度（観察回数で「近さ」が変わる）
- 鳥ごとの**鳴く/休むの状態機械**、共起度による**呼応**
- **群れ**（同一種を複数ずらして重ねる）
- 環境音の層（パッド・風・雨・風鈴）

これは**数百行の音響コード**で、この商品の心臓部そのもの。Flutter に持っていく場合、
`flutter_soloud` や `just_audio` などで**作り直す**ことになる。ここだけは
「移植」ではなく「再設計」に近い。**移行の成否はここで決まる。**

## 3. だから、順番はこうする

### ステップ0: 音のスパイク（1本だけ試す）← まずここ
**他は一切触らず、Flutter で「3羽が鳴くラジオ」だけを作る。**
- 鳥3羽の音源を鳴らし分ける／ゲートとフェード／環境音を1層重ねる
- 端末で鳴らして、いまの WebAudio 版と**聴き比べる**

これが通れば移行は成立する。通らなければ、**移行そのものを見送る**判断ができる。
**全面移行に踏み込む前に、いちばん危ない場所だけを確かめる**のが目的。

### ステップ1: ロジックの移植（テストが仕様書になる）
`engine.py` / `ecology.py` / `flock.py` / `badges.py` などは**純粋関数が中心**で、
**既に 207 のテストがある**。テストを先に Dart へ写せば、移植の正しさを機械で確認できる。
GloBI 由来のデータ（`predator_data.py` 等）は JSON なのでそのまま運べる。

### ステップ2: UI
図鑑・庭・ラジオ・使い方。ここは素直な作業。

### ステップ3: 切り替え
Play の同じアプリを Flutter 版で置き換える（パッケージ名は同じ）。
**セーブコードの互換**だけは必ず守る（既存ユーザーの進行データを壊さないため）。

## 4. 移行中の運営（ここを決めておかないと失敗する）

**全面書き直しの最大の失敗要因は「移行中、何も出荷できなくなること」。**
それを避けるため:

- **移行中も現行版は生かす。** 出せる改善（ストア文言・スクショ・SNS）は現行版で続ける。
- **現行版のコードは凍結気味に扱う。** 大きな機能追加は Flutter 側でやる。
  いま作った目覚まし（ネイティブ Java）は、**Flutter では素直に書き直せる**ので
  捨てる前提で構わない（設計と研究の結論は流用できる）。
- **期限を決める。** ステップ0に **1週間**。そこで判断する。

## 5. 失うもの（正直に）

- **Python での高速な試行**。データをいじって即確認、ができなくなる。
- **207 のテスト**は書き直しになる（ロジックの仕様としては再利用できる）。
- **Streamlit のウィジェット**（表・グラフ・フォーム）は自前で作ることになる。
- iOS を出すなら **Apple Developer Program 年 $99** と審査の手間が増える
  （出さないなら不要。Flutter でも Android だけで運用できる）。

## 6. 承認が必要な事項

1. **行き先を Flutter に定める**ことでよいか。
2. **ステップ0（音のスパイク・1週間）から始める**進め方でよいか。
   いきなり全面移行に入る判断もありうるが、その場合は
   「音が思ったように鳴らなかった」が数週間後に判明するリスクを取ることになる。
3. 移行中、現行版はどこまで手を入れるか（推奨: ストア・マーケ関連のみ）。

## 7. 補足 — いま急ぐ話ではない

DL はまだ 10+ で、プロダクトが当たるかは分かっていない。
**移行は「当たったときに耐えられる体」を作る作業**であって、
**当てる作業ではない**。当てる作業（ストアの名前・スクショ・SNS・AdMob 開通）と
並行して、ステップ0だけ静かに進めるのが、いちばん損が小さい。
