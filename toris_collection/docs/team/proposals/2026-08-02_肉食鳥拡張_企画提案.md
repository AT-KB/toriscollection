### 前提(CEO方針・2026-08-02・厳守)

- バイオーム(土地)の追加はしない(Kyoto / Charlotte の2つのまま)。
- 鳥の「厚み」を増やす。肉食鳥拡張はこの手段。
- 時刻連動は入れない。
- 植物・昆虫を独立の収集対象にはしない(収集対象は鳥のみ、`01_企画部.md` L36-37 の確定判断を維持)。

方向性(肉食鳥 = `bird→bird` 捕食の栄養段階の頂点を足す)は確定。本書は**詳細設計**を詰める。

## 1. 核となる設計判断:「罰しない」を最優先に据える(⚠最重要)

猛禽は「頂点捕食者」だが、Toris では**罰の装置にしない**。原則2(罰しない)と `disturbance.py` の
ガードレールに厳密に倣い、次の2点を**絶対条件**とする。

- **図鑑・会った日数・ラジオのキャストは、猛禽が来ても一切減らない。** 猛禽の在席中に小鳥が来なくても、
  過去に会った記録・観察数・鳴き声のアンロックは不変。撹乱で植物が倒れてもコレクションが減らないのと同じ。
- **猛禽の唯一のライブ効果は「柔らかく可逆なさざ波」に限定。** すなわち「**警戒心(`wariness`)が高い
  小鳥の"生の庭での到来率"を、猛禽の在席中だけ、係数で少し下げる**」。猛禽が去れば効果は即座に消える
  (残留・累積ペナルティなし)。撹乱のような「純減」は起こさない(植物にも図鑑にも触れない)。

そして体験の意味づけを**前向き**にする:猛禽との出会いは「あなたの庭が、頂点捕食者を養えるほど
豊かな小鳥の群れを抱えた」という**節目(祝福)+新しい収集対象**。「守れ!」「追い払え!」の類の
急かし・防衛ミニゲームは**作らない**(原則1・受動的)。UI 文言も「猛禽が来た=庭の豊かさの証」という
トーンにする(具体文言は別途、SNS部/開発部と詰める)。

### 「判断に迷ったら」4問(`01_企画部.md` L51-53)のセルフチェック

| 問い | 判定 | 理由 |
|---|---|---|
| 受動的か? | Yes | 防衛アクション・急かしを作らない。猛禽も時間経過で受動的に来る。 |
| 罰していないか? | Yes | 図鑑・会った日数・声は不変。効果は可逆なさざ波のみ。 |
| 声と癒しは無料か? | Yes | 猛禽の鳴き声も無料でラジオの音の幅を広げる(原則3)。課金要素は足さない。 |
| 生態に誠実か? | Yes | GloBI 実データにある捕食関係(§4)だけを使う。恣意的な「なぜ来たか」を足さない。 |

4問すべて Yes。かつ原則5(かわいさ)は「猛禽もかわいいドット絵で描く」で担保する。

## 2. 餌台/リスから切り離す(不採用構想の残骸を持ち込まない)

`species_expand.py` L6-8 の元構想は「餌台 → リス(*Sciurus*) → Hawk → 小鳥」の連鎖だった。しかし
**おやつ(人工餌台)は 2026-07-05 に不採用が確定**(`CONCEPT_v2.md` L92-97, L136-138)。
`feeder_chain.py` は残置・非配線のまま。したがって本提案では:

- 猛禽を**餌台・リス経由で成立させない**。`species_expand.py` の `mammal`(ハイイロリス/ニホンリス)候補は
  **今回のスコープ外**(収集対象は鳥のみ、という確定判断とも整合)。
- 猛禽は**既存の小鳥を直接 `preysOn`** する形だけで成立させる。栄養段階は
  `plant → insect → 小鳥 → 猛禽` の一本道で、餌台ノードを一切挟まない。

## 3. データ構造案(最小の追加)

猛禽も「鳥」の1レコードとして `BIRDS` に加える(既存スキーマを壊さない)。追加フィールドは2つだけ:

```
"coopers_hawk": {
    "name": "クーパーハイタカ", "scientific": "Accipiter cooperii", "english": "Cooper's Hawk",
    "color": "#5a6b7a",
    "eats_plants": [], "eats_insects": [],        # 既存スキーマ互換(空でよい)
    "temp_fit": (-6, 32), "biome_pref": ["charlotte"],
    "rarity": 0.75,                               # 希少 = 特別な訪問(§5 で要検証)
    "wariness": 0.5,                              # 猛禽自身は抑制対象ではない(下記参照)
    "role": "raptor",                             # ← 追加①:頂点捕食者フラグ
    "preys_on": ["northern_cardinal", "blue_jay", # ← 追加②:GloBI 種レベル一致(§4)
                 "american_robin", "carolina_wren",
                 "tufted_titmouse", "house_finch", "mourning_dove", "song_sparrow"],
    "description": "小鳥を狙って庭に現れる俊敏なタカ。多くの小鳥が茂みに身を隠す。",
}
```

- **`role`**:未指定の既存鳥は暗黙に `"songbird"`(通常鳥)。`role=="raptor"` のときだけ新ロジックが走る。
  既存35種は無変更で従来どおり動く(後方互換)。
- **`preys_on`**:`_data_raptor_globi.json` の `roster_prey_hits` から採る。§4 の方針で
  **`level:"species"`(種レベル一致)を優先採用**、`level:"genus"`(同属別種)は**保留 or 注記付き採用**。
- 既存フィールドとの整合:`rarity` / `biome_pref` / `temp_fit` はそのまま到来確率計算に載る。
  `eats_plants` / `eats_insects` は空でよい(猛禽の食料源は植物・昆虫ではなく小鳥。§3-1参照)。
- **`wariness` の扱い**:猛禽自身の `wariness` は「抑制する側」ではなく「抑制される側の係数」なので、
  猛禽レコードの `wariness` は演出用の既定値でよい(猛禽は小鳥ほど逃げない、という `ritual.py` 挙動)。

### 3-1. 猛禽の「食料源」は小鳥(データ上どう表すか)

`build_network` は `eats_plants`/`eats_insects` から流入エッジを張る(L242-247)。猛禽は小鳥を食べるので、
`preys_on` を根拠に **「在席中の獲物小鳥 → 猛禽」の流入エッジ**を張る(下記 §4-エンジン)。これは
「食物網スコア = 流入エッジ重みの合計」(`calculate_arrival_probability` L261-268)という**既存の考え方の
自然な延長**であり、新しい確率式を発明しない。

## 4. エンジン拡張の仕様(WHAT のみ / 実装は開発部)

コアループの順序(離れる→時間が進む→発見→なぜ来たか→図鑑・会った日数に積もる)は**一切変えない**。
猛禽は「発見」と「なぜ来たか」を一段深めるだけ。影響範囲を言葉で示す:

### (a) 猛禽の到来 = 獲物小鳥の「在席」に依存

- **意味**:猛禽は「今この庭に小鳥が実際に群れている」から来る(生態に誠実)。潜在的な食物網ではなく、
  **その時点で滞在中(resident)の獲物小鳥**の存在に依存させる。これが「庭が豊かになった節目」を成立させる。
- **`build_network`(L205-249)への影響**:猛禽ノードを追加する。ただし猛禽の流入エッジは
  植物・昆虫からではなく、**`preys_on` に含まれ、かつ現在 resident な小鳥**から張る。
  → `build_network` は現状 `resident_birds` を知らない(`run_turn` L322 が呼ぶ側で保持)。
  よって WHAT としては「猛禽の食物網スコアだけは resident 集合を入力に取る」形にする
  (実装形は開発部判断。例:`run_turn` 内で resident を渡して猛禽分の food_score を後付け計算)。
- **`calculate_arrival_probability`(L252-305)への影響**:`role=="raptor"` のとき、
  `food_score` を「在席中の獲物小鳥の数(または存在重み)」から算出する分岐を1つ足す。
  既存の飽和関数 `food_factor = 1 - 0.6^food_score`(L271)・`rarity_factor`・全体倍率 `×0.5` は流用。
  → 例:獲物小鳥が0羽なら `food_score=0 → food_factor=0 → 猛禽は来ない`。
    獲物が増えるほど猛禽の到来確率が上がる(頂点捕食者は豊かな系にだけ現れる)。**要検証:存在重みの
    与え方(1羽=1.0 か、獲物の rarity で重み付けか)。**

### (b) 猛禽の在席 = 警戒心の高い小鳥の到来率を係数で低下(可逆)

- **意味**:猛禽が滞在している間だけ、警戒心(`wariness`)の高い小鳥は身を隠し、**生の庭での到来率が
  一時的に下がる**。猛禽が去れば元に戻る(残留・累積なし)。
- **`run_turn`(L308-367)への影響**:到着判定ループ(L352-359)の直前で、resident に猛禽がいるかを見る。
  いれば、各獲物候補小鳥の到来確率 `p` に**抑制乗数**を掛ける:
  ```
  suppression = 1 - K_SUPPRESS * wariness      # 猛禽在席中の獲物小鳥のみに適用
  p_effective = p * suppression                # 猛禽不在なら乗数は掛けない(=完全に元通り)
  ```
  既存の `arrival_bonus_fn`(L346-347、広告リワード用の加算フック)と同じ「軽量・可逆フック」の作法に
  そろえる。**退去(`dep_rate` L332)は変更しない**(猛禽が小鳥を"追い出す"と純減=罰に近づくため、
  抑制は"来にくくする"側にのみ効かせ、"追い出す"側には効かせない)。
- **原則2との整合**:これは確率の一時的な低下であって、コレクションの減少ではない。猛禽が去れば
  翌サイクルから元の到来率に戻る。`disturbance.py` が「余計な係数を足さず自然に効かせる」思想の、
  最小限の対応物。

### 影響範囲まとめ(開発部への引き継ぎ用)

| 箇所 | 変更 | 後方互換 |
|---|---|---|
| `data.py` の `BIRDS` | 猛禽レコード追加(`role`/`preys_on`) | 既存35種は無変更 |
| `build_network` | 猛禽ノード追加、流入は resident 獲物から | `role` 無し種は従来どおり |
| `calculate_arrival_probability` | `role=="raptor"` の food_score 分岐 | 通常鳥の式は不変 |
| `run_turn` | 猛禽在席時のみ獲物小鳥に抑制乗数 | 猛禽不在なら計算結果は現状と同一 |

**猛禽が1羽もいない・データに `role` が無ければ、既存の全計算は今と完全に同じ**になるよう設計する
(開発部の「壊さない検証」で、猛禽データ0件時に既存 tests が全 pass することを受け入れ基準に含める)。

## 5. 数値バランスの論点(根拠併記・断定できない値は「要検証」)

指標は既存原則の「1日1回で気持ちよく積もる」(`01_企画部.md` L44)。猛禽は**日常ではなく"節目"**。

### 5-1. 猛禽の rarity(希少 = 特別な訪問にする)

- 既存の最希少帯は `pileated_woodpecker 0.80` / `kawasemi 0.70` / `uguisu 0.70`(`data.py` `_WARINESS` 近傍・
  `rarity` 群)。猛禽はそれらと同等以上の"特別さ"にしたい。
- **提案(要検証)**:クーパーハイタカ `rarity 0.75`、アカオノスリ `rarity 0.68`(ノスリは開けた土地で
  比較的見やすい)。`rarity_factor = (1 - rarity×0.85)×0.9`(L275)より、0.75 は係数 ≈ 0.32、
  0.68 は ≈ 0.38。獲物が十分いても全体倍率 `×0.5` と合わさり、**1サイクルで軽々は来ない**帯に収まる。
- 猛禽の到来は「獲物在席」ゲート(§4-a)も通るため、**二重の絞り**で"たまに訪れる特別な客"になる。

### 5-2. 抑制の強さ `K_SUPPRESS`(抑制が"罰"に見えない閾値)

獲物小鳥の `wariness`(実データ):`northern_cardinal 0.35` / `blue_jay 0.35` / `american_robin 0.30` /
`carolina_wren 0.45` / `tufted_titmouse 0.40` / `mourning_dove 0.35` / `song_sparrow 0.45` /
`house_finch`(既定 0.5) / `brown_thrasher 0.6`(最警戒)。

- **提案(要検証)**:`K_SUPPRESS = 0.30`。最も警戒心の高い `brown_thrasher(0.6)` でも
  `suppression = 1 - 0.30×0.6 = 0.82`(到来率 **-18%**)。中庸な `american_robin(0.30)` は
  `1 - 0.30×0.30 = 0.91`(**-9%**)。
- **意図**:体感で「猛禽がいる間は、臆病な子が少し顔を出しにくい」程度。**最大でも -20%前後**に抑え、
  "来なくなる"ではなく"少し控えめ"に留める。猛禽が去れば即 100% に戻る(可逆)。
- **上限ガード(要検証)**:`suppression` に下限(例 0.7)を設け、どんな `wariness` でも
  「-30%より下げない」。罰に見えない安全弁。**警戒心の低い種(スズメ 0.20 等)はほぼ無影響**で、
  「臆病な子ほど隠れる」という生態的直感とも一致する。

### 5-3. 到来頻度・在席の長さ

- **頻度**:上記 rarity + 獲物ゲートで、猛禽は**数日に一度の"節目"**の頻度感を狙う(要検証。
  実測は開発部のシミュレーションで詰める)。`max_arrivals_per_turn=1`(L309)は据え置き。
- **在席は短め(可逆さざ波を長引かせない)**:猛禽の退去率を通常鳥より高めに寄せると、さざ波が短時間で
  収まり「たまに来て、すぐ去る」節目らしさが出る。**要検証**(退去式 L332 を猛禽 role で微調整するか、
  それとも通常式のままにするか。§4-b で退去自体は罰化しないため、実装は最小に)。
- **同時1羽まで(要検証)**:頂点捕食者が複数同時は不自然かつ抑制が重なりすぎる。猛禽 role は
  `max_residents` とは別に「猛禽は同時1羽」を上限にするのが素直。

## 6. Kyoto のデータ被覆問題への判断(推奨を1つ明示)

`_data_raptor_globi.json` の実態:

- **Charlotte**:クーパーハイタカ = 現行の小鳥 **11種**を preysOn(うち種レベル一致 = Northern Cardinal /
  Blue Jay / American Robin / Carolina Wren / Tufted Titmouse / House Finch / Mourning Dove / Song Sparrow の
  **8種**、genus = American Goldfinch / Red-bellied Woodpecker / Brown Thrasher の 3種)。
  アカオノスリ = **9種**(種レベル = Blue Jay / American Robin / Mourning Dove / Song Sparrow の 4種、
  残り genus)。→ **データは厚い。栄養段階の頂点を誠実に描ける。**
- **Kyoto**:ツミ = GloBI が薄く **1種(スズメ *Passer montanus*、種レベル一致)のみ**。しかもスズメの
  `wariness` は 0.20 と低く、§5-2 の抑制がほぼ効かない(体感に乗らない)。→ **今のデータでは頂点捕食者
  レイヤーの手応えが作れない。**

### 推奨:【① Charlotte 先行】+【Kyoto は後続で猛禽を再選定(②)】

**MVP は Charlotte のみで猛禽レイヤーを実装し、Kyoto は保留**する。理由:

1. **原則4(生態に誠実)を最優先**:1種(スズメ)だけの薄い関係で頂点捕食者を"演出"すると、
   「恣意的な"なぜ来たか"を足さない」に反しかねない。データが語れる範囲で誠実に作る。
2. **原則2/体感**:スズメ中心では抑制さざ波が体感に乗らず(wariness 0.20)、猛禽の意味が伝わらない。
   厚いデータのある Charlotte でメカニクスを立ち上げ、手応えを確定させてから横展開するのが堅い。
3. **③(ツミ+スズメ1関係+注記)は"最小導入"としては可能だが非推奨**:誠実さと体感の両面で弱い。
   どうしても両バイオーム同時に猛禽を出したい経営判断がある場合の次善策として記録に留める。

**Kyoto の後続宿題(②の具体化・開発部へ)**:GloBI 被覆の良い近縁猛禽を再取得・検証する。候補は
**オオタカ *Accipiter gentilis*** または **ハイタカ *Accipiter nisus***(いずれも日本の里山〜市街地で
小鳥を広く襲い、GloBI の被覆がツミより厚い可能性が高い)。**猛禽種の最終確定前に、Charlotte と同じ手順で
GloBI 実データ(preysOn の roster ヒット)を引き、京都ロスター(スズメ/メジロ/ヒヨドリ/シジュウカラ等)との
種・属レベル一致数を確認する**こと。ツミに固執せず「データが語れる猛禽」を選ぶ。**要検証(GloBI 再取得)。**

## 7. genus レベル一致の扱い(誠実さの明文化)

`_data_raptor_globi.json` の `level:"genus"` は「GloBI に同属の別種(近縁種)を襲う記録がある」根拠で、
「近縁種を襲う」という生態的一般化の裏づけにはなるが、**その roster 種そのものの直接記録ではない**。方針:

- **`preys_on` は原則 `level:"species"` を採用**(§3 の8種はこれ)。
- **genus レベル(American Goldfinch / Red-bellied Woodpecker / Brown Thrasher 等)は、採用する場合
  データ由来を注記**して扱う(例:図鑑・生態ログ側で「近縁種の捕食記録に基づく」と明示)。恣意的に
  種一致と混同しない。MVP は species のみで始め、genus は評価後に追加する判断が最も誠実。**要検証。**
